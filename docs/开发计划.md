## 2. 总体架构与技术选型

### 2.1 架构总览：一份工程，三种导出

```
                    同一个 Godot 工程 tycoon/
                            │
      ┌─────────────────────┼──────────────────────┐
      ▼                     ▼                      ▼
 Windows 导出 exe       安卓导出 APK           Linux 无头导出
 (玩家客户端)           (玩家客户端)          (专用服务器, 跑在 VPS)
      └─────────────────────┴──────────────────────┘
                     ENet (UDP, 可靠信道)
                 规则引擎 = 同一份 GDScript 代码
```

- **权威服务器**：所有规则判定、倒计时、身份结算都在服务器跑；客户端只是"表现层"。手牌信息**只发给对应玩家**，从协议层防作弊。
- **规则逻辑零重复**：规则引擎写成不依赖场景的纯 GDScript（`class_name` 脚本），客户端（本地模式、动画预告）和服务器（权威判定）共用同一份代码。这是 Godot 方案对本项目最大的优势。
- 服务器判定是唯一的真值；客户端动画只是"演出"，以服务器消息为准回正。

### 2.2 选型要点

| 项 | 选择 | 说明 |
|---|---|---|
| 引擎 | Godot 4.x（当前最新稳定版） | 你已安装；2D/动画/音频/UI 全内置；免费无分成 |
| 语言 | GDScript（全量类型标注） | 规则引擎和 AI 是纯逻辑，类型标注保住可测性与 AI 辅助编码质量；不引入 C#（省掉移动端导出的额外复杂度） |
| 传输 | ENet（`ENetMultiplayerPeer`） | 原生应用专用：UDP 上自带可靠信道，比 WebSocket 省电省流量；回合制纸牌全部走 reliable 通道即可 |
| RPC | Godot 高层 multiplayer + `@rpc` 注解 | 服务器→指定客户端 / 客户端→服务器两类；消息 payload 用字典 + 服务端 schema 校验 |
| 单元测试 | 内置轻量 runner（零依赖；可选 gdUnit4 插件） | 规则逻辑纯函数化，任意 Godot binary headless 可跑，CI 无插件依赖（实施决策 2026-09-11） |
| 持久化 | 服务器战绩：JSON 文件起步（量大再换 godot-sqlite 插件）；客户端设置：`user://` ConfigFile | 零运维 |
| 服务器托管 | VPS + Docker（Debian slim + 无头导出产物） | 一台 2C4G 起步，几十个并发房间无压力（每房间 4 人） |

**决策记录**（为何弃 Web 方案）：目标是发布可安装应用、开发者本机已有 Godot；原生应用免去浏览器音频解锁/后台冻结/碎片化适配，且一份规则代码天然客户端服务器共享。代价是"发链接即玩"变成"发安装包"，已接受。

## 3. 游戏规则规格（开发用基线）

> 本节为基线摘要。完整规格见 `docs/规则规格.md`（v2.0）：含王补位精确算法、
> 托管与断线细则、术语表、13 条边界问答、配置总表与「规格↔实现↔测试」对照表。

### 3.1 标准规则

- 52 张牌 + 2 张 Joker（Joker 可在房间设置中关闭）。每人 13 张。
- 点序：3 < 4 < … < K < A < **2**；Joker 最大。
- 首局随机首出；之后每局由上一局"乞丐"先出。
- 出牌必须**同牌型且更大**，或 Pass；全员 Pass 则清桌，最后出牌者领出。
- 牌型 v1 支持：单张、对子、三条、四条、顺子（≥3 张连续，花色不限）。
- 最先出完手牌者结束，按出完顺序获得身份：**大富豪 → 富豪 → 平民 → 乞丐**。
- 一场对局默认打 3 局（可配置 1/3/5），按局积分累加，终局总分定胜负。

### 3.2 变体规则（全部做成房间配置项，默认开启"革命"）

| 配置项 | 默认 | 说明 |
|---|---|---|
| joker | 开 | 含 2 张 Joker，可压任意牌（都八等特殊效果 v1 不做） |
| revolution 革命 | 开 | 任一玩家一次出 ≥4 张同点 → 点序大小反转，持续到本局结束（两次革命叠加恢复） |
| stairs 階段 | 开 | 3 张以上同花色连续牌可作顺子出（革命时同样反转） |
| eightCut 8 切 | 关 | 出 8 直接清桌并领出 |
| 倒计时 | 20s | 出牌 20s / 换牌 15s，超时自动 Pass（须出时自动出最小合法牌） |

### 3.3 局间身份结算与换牌

- 单局积分：大富豪 +2、富豪 +1、平民 −1、乞丐 −2（3 局累加，可出现负分）。
- 局间换牌（第 2 局起）：**乞丐 → 大富豪** 交出手中最大的 2 张；**平民 ↔ 富豪** 互换最大的 1 张。换牌方向为"弱者给强者"，随后新局由乞丐先出。
- v1 为**自动交换**（标准规则强制交最大牌，无可选项），客户端播放交换展示；「自由挑选交换」列为后续变体。（实施决策 2026-09-11）

### 3.4 对局状态机（`src/rules/game_state.gd`）

```
WAITING(等人) → DEALING(发牌) → EXCHANGE?(换牌, 首局跳过)
  → PLAYING(领出/跟牌/Pass/清桌, 革命触发)
  → ROUND_END(身份结算+积分) ──还有下一局──► EXCHANGE
  └─────────最后一局─────────► GAME_END(总分/称号/再来一局)
```

实现为纯函数 `reduce(state: GameState, action: Action) -> GameState`，任何状态转换可在内置测试 runner 中无头穷举测试；服务器 `match.gd` 只负责"什么时候喂什么 action"。

## 4. 联机设计

### 4.1 消息协议（`@rpc` 事件，语义定义在 `src/protocol/msg.gd`）

```
客户端 → 服务器                          服务器 → 指定客户端
──────────────────────────────          ─────────────────────────────────
hello        {ver, session_token?}      welcome     {seat, room_state}
room_quick   {rules?}                   room_state  {players[], settings, host}
room_create  {rules}                    game_view   {自身手牌, 场况, 各家牌数}
room_join    {code}                     game_turn   {seat, remain_sec}
room_leave   {}                         game_played {seat, combo, remain}
room_kick    {seat}                     game_cleared{seat}        # 清桌
room_start   {}                         revolution  {on}          # 革命转场
game_play    {cards: [id]}              round_end   {ranks, points}
game_pass    {}                         game_end    {total, mvp}
exchange_pick{card_ids}                 game_exchange_done {picks}
emoji        {id}                       kicked      {reason}
                                        error       {code, msg}
```

要点：
- **`game_view` 按座位私发**（本人 13 张；别人只有牌数），`view.gd` 统一负责裁剪——这是防作弊的根基，也方便单测"任何状态不下泄他人手牌"。
- 服务端对每个动作校验合法性（轮次、牌型、是否 Pass），非法直接回 `error`，不影响权威状态。
- **版本握手**：`hello` 带客户端版本，与服务端不符则拒绝连接并返回下载提示。

### 4.2 房间与匹配

- 三种入口：**快速匹配**（排进等待中的公开房，满 4 自动开局）、**创建房间**（生成 6 位房间码发好友）、**输入房间码加入**。
- 房主可踢人、改规则、开局；开局后有人退出 → **AI 立即接管该座位**，对局不中断，本人回来可夺回。
- 一个房间一个独立 `match.gd` 实例；对局全内存态，`stats.gd` 只在终局写战绩。

### 4.3 断线重连与托管（手机体验的生死线）

- 进房时服务器发 **session_token**；安卓切后台/锁屏/电梯断网后 ENet 掉线，客户端每 2s 自动重试，连上后凭 token `hello` 回房，服务器重发完整 `game_view` 重建牌桌。
- 服务器保留离线座位 **30s 宽限**，期间和超时后都由 AI 托管；玩家重连即无缝夺回（托管期间已自动出的牌照常结算）。
- 所有等待都有服务器权威倒计时（UI 环形进度本地渲染），一个人挂机不会卡死三个人。

### 4.4 AI 策略（托管 + 本地模式共用）

- v1 规则式策略：能出则出"最小能压的"，剩牌少时激进；革命状态按反转后的点序评估；换牌阶段交出最大牌。
- 挂在 `src/rules/ai/`，服务器托管和本地调试模式调用同一实现，也直接复用于 fuzz 测试（AI 自打 1000 场断言无非法状态）。

## 5. 美术方案

### 5.1 风格方向（已定：A）

**和风 × 现代霓虹**：浮世绘纹样与和纸质感做底，描边扁平角色 + 霓虹金/朱红点缀。呼应大富豪的和风出身，又有别于传统棋牌审美；深色底在手机 OLED 上更省电。
关键词（固化到 `docs/美术风格指南.md`）：深靛蓝底 + 朱红/金色主色、和纸纹理、云纹/浪纹装饰线、粗描边扁平卡片、几何化无衬线中文标题字。

### 5.2 资产清单与省力策略

| 资产 | 数量 | 制作策略 |
|---|---|---|
| 牌面 | 54 | **程序化生成为主**：数字牌 2–10（36 张）同一模板批量渲染（`tools/card_gen` headless 出 PNG，换花色/点数/配色即可）；J/Q/K（12 张）3 个角色模板 ×4 花色换色；A 与 Joker（6 张）单独手绘特效牌。一致性极高、几乎零美术成本 |
| 牌背 | 2 | 和纹图案 1 + 革命特效牌背 1 |
| 牌桌/背景 | 2 | 横屏牌桌 1（下=自己，左/上/右=对手）+ 大厅背景 1 |
| 头像 | 8–12 | 和风角色头像 + 头像框一套（v1 不做自定义上传） |
| UI 套件 | ~40 元素 | 按钮 3 态、面板/弹窗、图标（房间码/倒计时/Pass/设置）、表情 8 个；全部走 Godot **Theme 资源**统一定义，换肤不改代码 |
| 特效 | 8 组 | 发牌、出牌飞行、清桌扫除、**革命全屏转场（红闪+点序反转演出）**、胜利/失败演出、换牌过场、倒计时告警 —— AnimationPlayer + Tween + 粒子实现 |

## 6. 音乐与音效方案

### 6.1 曲目/音效清单

| 类型 | 清单 | 风格 |
|---|---|---|
| BGM ×4 | 大厅、对局、革命时刻变奏、终局结算 | 和风 Lo-fi / 爵士小调，对局版节奏略紧但不过分抢注意力，无缝循环 |
| SFX ×~20 | 发牌、洗牌、出牌、Pass、清桌、按钮、倒计时滴答（最后 5s）、超时、革命警报、换牌、胜利/失败 jingle、表情弹出 | 短促干净，手机扬声器可辨识；重点打磨"出牌手感"这一颗（每局播放几百次） |

### 6.2 制作方式

- BGM：AI 音乐生成（Suno 等）出 6~8 候选 → 挑 4 首剪辑定循环点 → OGG Vorbis 导入（Godot 导入面板开 loop）。
- SFX：freesound / jsfxr 为主 → WAV 导入（短音效延迟最低）。

### 6.3 技术实现要点

- Godot **音频总线**：Master → BGM / SFX 两条子总线，各自音量；`settings.gd` 存 `user://settings.cfg`。
- 浏览器音频解锁问题不存在（原生应用），但真机用例仍要覆盖：锁屏恢复、来电打断后 BGM 恢复。
- 革命转场等"演出音"与 UI 音分离总线，革命警报可临时压低 BGM（sidechain 或手动 ducking）。

## 9. 部署与运维

- 单台 VPS（2C4G 起步）+ Docker：`deploy/Dockerfile`（Debian slim + Linux 无头导出产物），仅开放 ENet UDP 端口（如 24565）；无需 nginx/域名证书（ENet 非 WebSocket；如需加密可后置换 DTLS peer）。
