# 路线图 · 下一阶段待办（架构师视角）

> 更新: 2026-09-14 · 基于 v1.1.0（本地普通/肉鸽 + 联机 + 经济/留存闭环已就位）

## 已完成基线（不重复展开）

- 规则引擎：大富豪全规则 + 肉鸽命运卡（引擎层，可重放）
- 联机：Tailscale + 局域网 UDP 发现 + 多地址邀请码；专用/内嵌双服务器形态
- 经济与留存：金币/钻石、装扮商城、双倍钻石卡、每日首胜、每日签到、成就(10)、
  对局记录(20 条)、称号
- 质量：零依赖测试框架(10 万+断言)、自适应布局普查、E2E 双链路、双端导出

## P1 · 联机肉鸽（引擎已就绪，差服务端同步）

设计草案：
1. `room.settings` 增加 `"rogue": true`（房主开房可选）；`room.start()` 构造
   `new_match(cfg)` 时带 rogue —— 服务端每局抽卡逻辑与本地完全同源（seed+局号）。
2. 协议：`s_game_view` 增加 `rogue_mod` 字段（当前局命运卡 id）；
   局开始时新增广播事件 `s_rogue_reveal {mod, round}`。
3. 客户端：table 联机分支收到 `s_rogue_reveal` → 复用现有揭示弹窗；
   联机 label 复用 `_update_rogue_lbl`（当前仅本地分支显示）。
4. 测试：net_logic 增加 rogue 房间流；fuzz 无需变化（引擎不变）。
工作量预估：1 个会话；风险低（不碰 ENet/重连通路）。

## P2 · 服务器权威经济（跨设备钱包）

现状钱包为本地存档（可改档、换设备丢失）。方案：
1. 阶段一：本地钱包 + 云备份码（导出/导入 JSON+签名校验），零服务器改动。
2. 阶段二：dedicated server 挂 `--wallet-db user://wallets.db`（SQLite 或 JSON 分片），
   客户端以 client_id 幂等上报对局结果，服务端复算积分发放（防作弊关键：
   服务端只信任自己的 MatchController 结算，不信任客户端上报的分数）。
3. 迁移：首登本地钱包快照上云，之后以云端为准、本地做缓存。
风险：中（需要迁移与幂等设计）；建议在联机肉鸽之后做。

## P3 · 对局回放

基础已具备：`seed + cfg` 可完整重放任何本地局（`_deal_round` 按局定随机）。
方案：对局记录条目扩容 `{seed, cfg, actions: [...]}` 落盘；
回放器 = 逐条 `GameState.apply` + table 只读渲染（禁操作）。
工作量：1-2 个会话；建议在联机肉鸽之后（复用联机的观战渲染路径）。

## P4 · 成就 II / 赛季

- 成就 II：肉鸽专项（抽到每种命运卡至少一次 / 肉鸽胜场 / 双倍赌局翻盘），
  需要本地统计新增 rogue 维度计数（当前 grant 不区分模式 → 需在
  `push_history` 之上加统计聚合，或 grant 增加 meta 参数）。
- 赛季：称号按月重置 + 赛季徽章；依赖 P2 云端结算才有公信力，建议 P2 后。

## P5 · 技术债

- `table.gd`（1300+ 行）本地/联机双路径耦合：建议抽 `LocalMatchDriver` 与
  `OnlineMatchDriver` 两个策略类，table 只留渲染与输入（重构窗口：
  无新功能的一个会话，靠现有 10 万断言兜底）。
- `lobby.gd`（1100+ 行）入口/房间双视图 + 局域网发现 + 邀请码：同类拆分。

## 明确不做（记录原因）

- 账号密码体系：目标场景是亲友局，client_id + 云备份码已覆盖，微信/QQ 登录
  引入审核与合规成本，收益不匹配。
- 排位匹配（ELO）：在线人数不足时匹配体验差，待联机规模起来再评估。
